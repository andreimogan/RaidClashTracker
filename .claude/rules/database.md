- **One database, one pool.** `lib/db.ts` owns the connection and exports exactly four names — `Db` (a re-export of postgres.js's client type, which is named **`Sql`**, so nothing else imports `postgres` directly), `databaseUrl()`, `getDb()`, `closeDb()`. The pool is a **`globalThis` singleton, never a module `const`**: Next dev HMR re-evaluates modules and a module-level pool would open one per reload and exhaust Supabase's pooler. Options: `prepare: false` (mandatory on the transaction pooler), `max: 3`, an `idle_timeout`. Never add a second DB, a pointer file, or any runtime switch, and keep `lib/db.ts` free of filesystem reads/writes — every page render goes through it, so a `readFileSync` there costs every route.
- **A multi-query read must run inside one `sql.begin()`, or it can hang.** `max` is a **correctness bound, not pooler politeness.** Issuing more concurrent queries than `max` against Supabase's transaction pooler **deadlocks forever** once the pool already holds an established connection — the normal state of a running server. Measured deterministically at four `max`/concurrency combinations (3/4, 4/8, 8/16, 10/12); **no value of `max` is safe**, raising it only moves the cliff. So a read needing several queries takes **one** connection and pipelines on it — `await getDb().begin("read only", (sql) => [ …queries ])`, as `lib/data.ts` `loadDataset()` and `lib/backup.ts` `exportBackup()` both do. **Never `Promise.all` a set of queries straight off `getDb()`.** Queueing whole *transactions* past `max` is safe (30 concurrent `loadDataset()` calls against `max: 3` all complete). Note the in-transaction client is a **different type**, `TransactionSql`: like `Sql` it extends `ISql`, but it does **not** extend `Sql`, so it is *not* assignable to `Db`. A helper meant to accept either would have to be typed on their shared supertype, `ISql` — and **`lib/db.ts` does not export it.** Its exports are exactly the four above, which is a checkable invariant, and nothing needs `ISql` today: the helpers that take a client (`persist()`, `resetDatabase()`) take `Db` and are called with the pool. Add the re-export in the same change that first needs it, not in advance. Until then the failure mode is a compile error at the call site, not a silent trap.
- **A wrong-password check trips the pooler's circuit breaker, and it does not report `28P01`.** Supabase's pooler counts failed authentications per project: a server left retrying a bad password makes it refuse **all** new connections to the project — including legitimate ones from the owner's own dashboard — with **`XX000` `(ECIRCUITBREAKER) too many authentication failures, new conn`**, *not* the `28P01` a single bad login gives. It self-clears (measured ~100 s; one incident this order cleared in ~75 s) with nothing altered on the Supabase side. Two consequences. (1) Any phase re-running the three-state check — Phases 3 and 4 both do — keeps state 3 **short-lived** and tears the server down immediately, killing **by port and then verifying the port is actually free** — a `next start` launched through a wrapper script or with `shell: true` orphans the real server when you kill the launcher's PID, and the orphan goes on retrying (this is how the incident happened). If `ECIRCUITBREAKER` appears, suspect a leftover process first — it says nothing about the credentials or the code. (2) It is the sharpest argument for the `42P01`-only allowlist below: **the pooler can report an authentication failure under a code that has nothing to do with authentication.** Any rule shaped as "fall back to demo unless the error is one of these known connection failures" would therefore let a real outage through as fake clan data. Allowlist the one code that means "not migrated yet"; rethrow everything else.
- **Never leak the connection URI.** It contains the password. `databaseUrl()`'s value is never logged, returned to a client, rendered in a page, or included in an error message; it lives in `.env.local` only, and every doc, example and ledger uses a placeholder.
- **Superseded decision — SQLite / libSQL / Turso.** This file used to *lock* a dual-engine rule: keep all SQL portable between the local SQLite file (`data/clash.db`, spoken to via `@libsql/client`) and Turso, its hosted twin, so deploying would need no code change. Phase 2's port to Supabase Postgres **supersedes** it. `@libsql/client` is uninstalled, no database file is read at runtime, and nothing has to stay portable — target Postgres directly. The engine names are written out on purpose: a reader arriving with the old vocabulary greps for `Turso` or `SQLite` and must land here rather than find silence. `docs/build-log.md` carries the full history of both decisions.
- **Migrations are numbered, forward-only SQL files** in `supabase/migrations/`, applied in filename order by `npm run db:migrate`. **`db:migrate` keeps no applied-migrations table** — it re-applies every file on every run — so **every migration must be written idempotently**: `create table if not exists`, `create or replace view`, `add column if not exists`, and a data migration needs its own guard (`on conflict do nothing`). That requirement is what makes re-running safe; it is a rule for new migrations, not just an observation about the existing ones. Tracking was rejected deliberately: the owner also applies SQL in Supabase's dashboard, and a tracking table would desynchronise the moment that happens — lying exactly when you need it to be right. **An applied migration is never edited** — a schema change means a new numbered file. There is no down-migration path.
- **Types are load-bearing:** `total_damage` is `bigint` (real values reach 5.8e10, ~27× int4's ceiling) and reads back as a JS **string**, so coercion belongs in `lib/data.ts`'s row mappers, never in `compute.ts`. Verify a column's read-back type before choosing it.
- **Never break the demo fallback, and never widen it.** It fires on exactly two conditions: `databaseUrl()` is null, or a caught error's code is `42P01` (undefined table). Every other failure — bad password, DNS, pooler exhaustion, paused project — must rethrow and reach `app/error.tsx`. A reachable but empty database renders genuinely empty. A connection outage must never render `lib/mock-data.ts` as real clan data.
