- **One database, one pool.** `lib/db.ts` owns the connection and exports exactly four names — `Db` (a re-export of postgres.js's client type, which is named **`Sql`**, so nothing else imports `postgres` directly), `databaseUrl()`, `getDb()`, `closeDb()`. The pool is a **`globalThis` singleton, never a module `const`**: Next dev HMR re-evaluates modules and a module-level pool would open one per reload and exhaust Supabase's pooler. Options: `prepare: false` (mandatory on the transaction pooler), `max: 3`, an `idle_timeout`. Never add a second DB, a pointer file, or any runtime switch, and keep `lib/db.ts` free of filesystem reads/writes — every page render goes through it, so a `readFileSync` there costs every route.
- **A multi-query read must run inside one `sql.begin()`, or it can hang.** `max` is a **correctness bound, not pooler politeness.** Issuing more concurrent queries than `max` against Supabase's transaction pooler **deadlocks forever** once the pool already holds an established connection — the normal state of a running server. Measured deterministically at four `max`/concurrency combinations (3/4, 4/8, 8/16, 10/12); **no value of `max` is safe**, raising it only moves the cliff. So a read needing several queries takes **one** connection and pipelines on it — `await getDb().begin("read only", (sql) => [ …queries ])`, as `lib/data.ts` `loadDataset()` and `lib/backup.ts` `exportBackup()` both do. **Never `Promise.all` a set of queries straight off `getDb()`.** Queueing whole *transactions* past `max` is safe (30 concurrent `loadDataset()` calls against `max: 3` all complete). Note the in-transaction client is a **different type**, `TransactionSql`: like `Sql` it extends `ISql`, but it does **not** extend `Sql`, so it is *not* assignable to `Db`. A helper meant to accept either would have to be typed on their shared supertype, `ISql` — and **`lib/db.ts` does not export it.** Its exports are exactly the four above, which is a checkable invariant, and nothing needs `ISql` today: the helpers that take a client (`persist()`, `resetDatabase()`) take `Db` and are called with the pool. Add the re-export in the same change that first needs it, not in advance. Until then the failure mode is a compile error at the call site, not a silent trap.
- **A wrong-password check trips the pooler's circuit breaker, and it does not report `28P01`.** Supabase's pooler counts failed authentications per project: a server left retrying a bad password makes it refuse **all** new connections to the project — including legitimate ones from the owner's own dashboard — with **`XX000` `(ECIRCUITBREAKER) too many authentication failures, new conn`**, *not* the `28P01` a single bad login gives. It self-clears (measured ~100 s; one incident this order cleared in ~75 s) with nothing altered on the Supabase side. Two consequences. (1) Any phase re-running the three-state check — Phases 3 and 4 both do — keeps state 3 **short-lived** and tears the server down immediately, killing **by port and then verifying the port is actually free** — a `next start` launched through a wrapper script or with `shell: true` orphans the real server when you kill the launcher's PID, and the orphan goes on retrying (this is how the incident happened). If `ECIRCUITBREAKER` appears, suspect a leftover process first — it says nothing about the credentials or the code. (2) It is the sharpest argument for the `42P01`-only allowlist below: **the pooler can report an authentication failure under a code that has nothing to do with authentication.** Any rule shaped as "fall back to demo unless the error is one of these known connection failures" would therefore let a real outage through as fake clan data. Allowlist the one code that means "not migrated yet"; rethrow everything else.
- **Never leak the connection URI.** It contains the password. `databaseUrl()`'s value is never logged, returned to a client, rendered in a page, or included in an error message; it lives in `.env.local` only, and every doc, example and ledger uses a placeholder. **A raw driver error is a leak of the same class:** postgres.js builds connection errors as `write/connect <code> <host>:<port>`, so echoing one to a client publishes the pooler hostname — and a `28P01` message carries the connection's user name, which embeds the project ref. Every route that catches a database error maps it to its own sentence plus the bare PG code; never pass `err.message` through when the error carries a string `.code`.
- **Superseded decision — SQLite / libSQL / Turso.** This file used to *lock* a dual-engine rule: keep all SQL portable between the local SQLite file (`data/clash.db`, spoken to via `@libsql/client`) and Turso, its hosted twin, so deploying would need no code change. Phase 2's port to Supabase Postgres **supersedes** it. `@libsql/client` is uninstalled, no database file is read at runtime, and nothing has to stay portable — target Postgres directly. The engine names are written out on purpose: a reader arriving with the old vocabulary greps for `Turso` or `SQLite` and must land here rather than find silence. `docs/build-log.md` carries the full history of both decisions.
- **Migrations are numbered, forward-only SQL files** in `supabase/migrations/`, applied in filename order by `npm run db:migrate`. **`db:migrate` keeps no applied-migrations table** — it re-applies every file on every run — so **every migration must be written idempotently**: `create table if not exists`, `create or replace view`, `add column if not exists`, and a data migration needs its own guard (`on conflict do nothing`). That requirement is what makes re-running safe; it is a rule for new migrations, not just an observation about the existing ones. **Caveat on `create or replace view`: it is idempotent for the view's *definition* and silently destructive to its *options*** — see the `reloptions` invariant below. Tracking was rejected deliberately: the owner also applies SQL in Supabase's dashboard, and a tracking table would desynchronise the moment that happens — lying exactly when you need it to be right. **An applied migration is never edited** — a schema change means a new numbered file. There is no down-migration path.
- **The `public` API is locked down, and the lockdown has four levers that fail in opposite directions.** `supabase/migrations/0002_lock_down_public_api.sql` (applied; never edit it) closed anonymous PostgREST access to the whole schema. Measured before → after on the live project: `anon`/`authenticated` grant rows in `public` **35 each → 0** · `relacl` on all five objects `{postgres,anon,authenticated,service_role}` → **`{postgres,service_role}`** · `relrowsecurity` **false ×4 → true ×4** · `pg_policies` in `public` **0 → 0** · view `reloptions` `null` → **`{security_invoker=on}`** · every `GET /rest/v1/<object>` with the publishable key **200 `[]` → 401 `42501 permission denied`**, and `POST /rest/v1/members` **201 → 401, nothing created**. The migrate role is `postgres`, which **owns** all five objects and has **`rolbypassrls = true`** — so RLS never applies to the app, on two independent grounds. The five invariants below are the ones a future migration can silently void:
  - **Lever 4 revokes grants, not RLS.** `alter default privileges … revoke all on tables` stops a *future* table inheriting `anon` grants — proved with a throwaway table created as `postgres`, which came out with grantees `{postgres, service_role}` and **0** `anon`/`authenticated` grant rows — but it **does not enable RLS on it** (the probe table had `relrowsecurity = false`). **Every new table in `public` needs its own `enable row level security` line in the migration that creates it.** Otherwise the table looks fine until someone runs the `grant select on all tables in schema public to anon` copy-paste, at which point it is fully readable with the publishable key, because there are no policies to stop it.
  - **`create or replace view` resets `reloptions` to `null`**, wiping `security_invoker` (measured; `relacl` is *not* reset, so the revokes survive). This is not hypothetical: `0001_init.sql`'s bare `create or replace view` un-does lever 3 on every migrate run, and only filename order saves the full run — `0002` re-sets it afterwards. Applying **`0001` alone** (e.g. pasting it into the Supabase SQL editor) leaves the view running with owner rights, and only lever 2's revoke keeps that from being an exposure. **Anything that recreates `member_clash_averages` must re-assert `alter view … set (security_invoker = on)` in the same file.** Note RLS cannot substitute here: `alter view … enable row level security` is invalid syntax — **RLS does not exist on views**, and without `security_invoker` a view bypasses its tables' RLS entirely.
  - **Create tables via `supabase/migrations/` + `npm run db:migrate`, never the dashboard's Table Editor.** There is a second `pg_default_acl` entry belonging to **`supabase_admin`** that still grants `anon`/`authenticated` on future tables, and altering another role's default privileges needs superuser (measured: `42501 permission denied to change default privileges`). Lever 4 holds for our migrations because they create as `postgres` — but **a table created through the dashboard UI can be born with the door open.**
  - **`alter default privileges` is scoped to the granting role** and must run as the role that will create the objects. Here `postgres` is both the migrate role and the owner, so it lines up; **changing the migrate role silently voids lever 4.**
  - **Lever 4 is `ON TABLES` only.** The `postgres` default ACL still grants `anon`/`authenticated` `EXECUTE` on future **functions** and `rwU` on future **sequences** in `public`. A migration adding either must revoke explicitly. Separately, **`service_role` retains full DML** on all five objects — untouched by design. It is a secret key; if it ever reaches a browser the lockdown is moot.
- **"RLS enabled, no policies" is the intended end state — do not resolve the advisory.** The Supabase dashboard flags those four tables because zero policies means nothing is readable through PostgREST, which is exactly the point: the app reads as the owning role over postgres.js, not over `/rest/v1`. **`create policy` is lever 1's documented failure mode** — a well-meaning `for select using (true)` for a "public leaderboard" reopens the hole the migration closed. If a genuinely public read is ever wanted, that is a deliberate order with its own gate, not a warning to silence. `force row level security` is likewise deliberately absent: it buys nothing (anon/authenticated are already refused at the grant layer) and arms a landmine for the day the app connects as a role **without** `bypassrls`. `revoke usage on schema public` is absent because PostgREST introspection, Realtime and the dashboard's API-docs generator may depend on it — unverified, so untouched.
- **Types are load-bearing:** `total_damage` is `bigint` (real values reach 5.8e10, ~27× int4's ceiling) and reads back as a JS **string**, so coercion belongs in `lib/data.ts`'s row mappers, never in `compute.ts`. Verify a column's read-back type before choosing it.
- **Never break the demo fallback, and never widen it.** It fires on exactly two conditions: `databaseUrl()` is null, or a caught error's code is `42P01` (undefined table). Every other failure — bad password, DNS, pooler exhaustion, paused project — must rethrow and reach `app/error.tsx`. A reachable but empty database renders genuinely empty. A connection outage must never render `lib/mock-data.ts` as real clan data.
