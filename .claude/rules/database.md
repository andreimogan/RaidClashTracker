- **One database, one pool.** `lib/db.ts` owns the connection and exports exactly four names — `Db` (a re-export of postgres.js's client type, which is named **`Sql`**, so nothing else imports `postgres` directly), `databaseUrl()`, `getDb()`, `closeDb()`. The pool is a **`globalThis` singleton, never a module `const`**: Next dev HMR re-evaluates modules and a module-level pool would open one per reload and exhaust Supabase's pooler. Options: `prepare: false` (mandatory on the transaction pooler), `max: 3`, an `idle_timeout`. Never add a second DB, a pointer file, or any runtime switch, and keep `lib/db.ts` free of filesystem reads/writes — every page render goes through it, so a `readFileSync` there costs every route.
- **The connection string resolves from two names — `DATABASE_URL`, then `POSTGRES_URL` — first non-blank after `trim()` wins.** `CONNECTION_VARS` (`lib/db.ts:41`) is walked by an internal `resolveConnection()` returning `{name, url}`; `databaseUrl()` is `resolveConnection()?.url ?? null`, with the same signature and the same blank-counts-as-unset contract as before. `DATABASE_URL` is what `.env.local`, CI and every `scripts/` entry set, so local behaviour is unchanged; `POSTGRES_URL` is what the Supabase↔Vercel integration creates, so **a deployment needs no manual `DATABASE_URL`** and explicit still beats inherited. **Inheriting `POSTGRES_URL` is both what makes the deploy work and the new hazard the chain introduced.** `POSTGRES_URL` is a *generic* name, not a Supabase one: any environment that already exports it for an unrelated reason — a second Postgres/Neon integration on the same Vercel project, a docker-compose Postgres image, a shell profile set for `psql` work — now becomes this app's database, where before Phase 4 it landed harmlessly in demo mode. If that other database happens to be migrated, the schema matches and **writes go there silently**, with no error and nothing in the UI to say which database it reached. So: **set `DATABASE_URL` explicitly wherever you can** (it wins, and it is unambiguous), and treat an unexplained `POSTGRES_URL` in an environment as a question, not as furniture. **Do not "simplify" this to `process.env.DATABASE_URL ?? process.env.POSTGRES_URL`.** `""` is not nullish, so a present-but-empty `DATABASE_URL` — trivially created in a Vercel project by adding the name and saving with no value — would win the chain, shadow the integration's copy, and drop the deployment into **demo mode while holding a variable that looks set**. That is exactly the Phase 4 bug (a public URL serving `lib/mock-data.ts`), re-armed by a refactor that reads better. The `??` form is the natural cleanup and someone will propose it. The integration's other two connection strings are **never read**: `POSTGRES_URL_NON_POOLING` is the **direct 5432** endpoint, which on serverless opens one real Postgres connection per invocation and exhausts the project's limit under load, and `POSTGRES_PRISMA_URL` is the pooled endpoint with Prisma-only query parameters (`connection_limit`, `pgbouncer=…`) that mean nothing to postgres.js. Both are *named* in `lib/db.ts` and `.env.example` on purpose — they are the first thing a reader debugging a dead deployment reaches for. Living doc: `docs/reference/deployment.md`.
- **The pooled port is checked and reported, never assumed — and the check must stay a warning, not a throw.** Confidence is deliberately medium: Vercel's marketplace page says `POSTGRES_URL` is the transaction pooler (`6543`), **Supabase's own integration doc lists the names and says nothing about ports.** So `warnIfNotPooledPort()` (`lib/db.ts:81`) emits **one `console.warn` per process** when the resolved URI is not on `6543`, naming **only the port and the variable it came from**, because the URI carries the password (see the no-leak rule below). **State the no-leak property precisely — half of it is absolute and half is not.** Absolute, on *any* input: the line can never contain a **host, user name, database name, project ref, password body or `postgresql://`**, because the only two values interpolated are `conn.name` (a literal from `CONNECTION_VARS`) and WHATWG `URL.port`, which is digits or empty by construction. **Not absolute:** "no part of the password can reach the line". WHATWG `URL` ends the authority at the first `/`, so a password whose leading digits are followed by an *unencoded* `/` parses those digits as the port — measured this session:
  ```
  postgresql://postgres.abcdefghij:12345/MyRealPassword@aws-0.pooler.supabase.com:6543/postgres
  → "DATABASE_URL points at port 12345, not the pooled 6543 …"
  ```
  (that input has no `@`-terminated userinfo as far as `URL` is concerned, so it reads `postgres.abcdefghij` as the *host* — which is still never printed). The exposure is tightly bounded, and tighter than "≤5 digits": the run must parse as a valid port, so `…:99999/…` and `…:123456/…` both throw `ERR_INVALID_URL` and log **nothing**; leading zeros are normalised away (`…:0123/…` → `123`), so the printed value is not even a faithful prefix; a percent-encoded `/` (`…:12345%2FPw@…`) parses correctly and prints `6543`. A conforming postgres URI must percent-encode `/` in a password, and Supabase-generated passwords are alphanumeric. **Decision: the code stays as it is and the claim gets qualified**, because the printed value is `URL.port` — digits only, ≤5 of them, numerically ≤65535 — and it reaches a **server log the owner already controls**, not a client response. Sanitising further would add a branch to the one function on every render's path in exchange for at most five digits of a self-inflicted malformed password. Written down so nobody re-asserts the absolute form later. Three details are load-bearing and each has a reason: it **does not throw** (`prepare: false` is unconditional, so a session-pooler or direct URI still works, and a site up on the wrong port beats a site that is down); **no explicit port is reported as `5432 (implicit, no port in the URI)`**, since an implicit direct connection is the worst case and must not pass unwarned; and an **unparseable URI logs nothing at all**, because anything printed there risks echoing the string and postgres.js will fail on its own terms anyway. The once-per-process flag rides on `globalThis` (`__raidClashPortChecked`) for the same reason the pool does — a module-level flag resets on every HMR reload and the warning would repeat per reload. On serverless, "once per process" means once per warm instance, so **absence of the line in a log tail is not proof the port is right.** **`closeDb()` deliberately does not re-arm the flag** — it clears `__raidClashDb` only, so measured in one process: `getDb()` on 6543 → `closeDb()` → `getDb()` on 5432 warns **zero** times. That is the spec, not a defect: the check exists to tell an operator once that a deployment's variable is wrong, and re-arming it would make a CLI script that reconnects re-warn for the same misconfiguration. The practical consequence is for whoever tests it — **each port case needs its own process** (this is why t1 ran one `npx tsx` per case), and a test that calls `closeDb()` between cases silently proves nothing.
- **A multi-query read must run inside one `sql.begin()`, or it can hang.** `max` is a **correctness bound, not pooler politeness.** Issuing more concurrent queries than `max` against Supabase's transaction pooler **deadlocks forever** once the pool already holds an established connection — the normal state of a running server. Measured deterministically at four `max`/concurrency combinations (3/4, 4/8, 8/16, 10/12); **no value of `max` is safe**, raising it only moves the cliff. So a read needing several queries takes **one** connection and pipelines on it — `await getDb().begin("read only", (sql) => [ …queries ])`, as `lib/data.ts` `loadDataset()` and `lib/backup.ts` `exportBackup()` both do. **Never `Promise.all` a set of queries straight off `getDb()`.** Queueing whole *transactions* past `max` is safe (30 concurrent `loadDataset()` calls against `max: 3` all complete). Note the in-transaction client is a **different type**, `TransactionSql`: like `Sql` it extends `ISql`, but it does **not** extend `Sql`, so it is *not* assignable to `Db`. A helper meant to accept either would have to be typed on their shared supertype, `ISql` — and **`lib/db.ts` does not export it.** Its exports are exactly the four above, which is a checkable invariant, and nothing needs `ISql` today: the helpers that take a client (`persist()`, `resetDatabase()`) take `Db` and are called with the pool. Add the re-export in the same change that first needs it, not in advance. Until then the failure mode is a compile error at the call site, not a silent trap.
- **A wrong-password check trips the pooler's circuit breaker, and it does not report `28P01`.** Supabase's pooler counts failed authentications per project: a server left retrying a bad password makes it refuse **all** new connections to the project — including legitimate ones from the owner's own dashboard — with **`XX000` `(ECIRCUITBREAKER) too many authentication failures, new conn`**, *not* the `28P01` a single bad login gives. It self-clears (measured ~100 s; one incident this order cleared in ~75 s) with nothing altered on the Supabase side. Two consequences. (1) Any phase re-running the three-state check — Phases 3 and 4 both do — keeps state 3 **short-lived** and tears the server down immediately, killing **by port and then verifying the port is actually free** — a `next start` launched through a wrapper script or with `shell: true` orphans the real server when you kill the launcher's PID, and the orphan goes on retrying (this is how the incident happened). If `ECIRCUITBREAKER` appears, suspect a leftover process first — it says nothing about the credentials or the code. (2) It is the sharpest argument for the `42P01`-only allowlist below: **the pooler can report an authentication failure under a code that has nothing to do with authentication.** Any rule shaped as "fall back to demo unless the error is one of these known connection failures" would therefore let a real outage through as fake clan data. Allowlist the one code that means "not migrated yet"; rethrow everything else.
- **Never leak the connection URI.** It contains the password. `databaseUrl()`'s value is never logged, returned to a client, rendered in a page, or included in an error message; it lives in `.env.local` locally and in the deployment's own environment (as the integration's `POSTGRES_URL`) — never in a tracked file, and every doc, example and ledger uses a placeholder. **A raw driver error is a leak of the same class:** postgres.js builds connection errors as `write/connect <code> <host>:<port>`, so echoing one to a client publishes the pooler hostname — and a `28P01` message carries the connection's user name, which embeds the project ref. Every route that catches a database error maps it to its own sentence plus the bare PG code; never pass `err.message` through when the error carries a string `.code`.
- **Superseded decision — SQLite / libSQL / Turso.** This file used to *lock* a dual-engine rule: keep all SQL portable between the local SQLite file (`data/clash.db`, spoken to via `@libsql/client`) and Turso, its hosted twin, so deploying would need no code change. Phase 2's port to Supabase Postgres **supersedes** it. `@libsql/client` is uninstalled, no database file is read at runtime, and nothing has to stay portable — target Postgres directly. The engine names are written out on purpose: a reader arriving with the old vocabulary greps for `Turso` or `SQLite` and must land here rather than find silence. `docs/build-log.md` carries the full history of both decisions.
- **Schema, migrations and the PostgREST lockdown are `.claude/rules/supabase-schema.md`** (`paths: ["supabase/**", "scripts/db-migrate.ts"]`). Two consequences reach the files *this* rule covers and are restated here rather than looked up: **`total_damage` is `bigint` and reads back as a JS string**, so `lib/data.ts`'s four row mappers are the single coercion boundary and `compute.ts` must never do the coercion; and **`npm run db:migrate` re-applies every file every run** (no applied-migrations table), so `scripts/db-migrate.ts` must stay safe to re-run.
- **Never break the demo fallback, and never widen it.** It fires on exactly two conditions: `databaseUrl()` is null, or a caught error's code is `42P01` (undefined table). Every other failure — bad password, DNS, pooler exhaustion, paused project — must rethrow and reach `app/error.tsx`. A reachable but empty database renders genuinely empty. A connection outage must never render `lib/mock-data.ts` as real clan data.
- **Static prerendering is the one way the demo dataset gets laundered into "real" HTML — and it is a *rendering* rule, kept in `.claude/rules/rendering.md`.** The short version, because it is the database consequence: the four `searchParams` data pages are dynamic *only* because each awaits `searchParams` (the fifth, `/members`, awaits nothing and is held dynamic by an explicit `force-dynamic`), so a page that stopped doing that without declaring `force-dynamic` in the same change would be prerendered at build time and would bake **whatever `lib/data.ts` returned in the build environment** into HTML served to every visitor — the demo dataset, if that environment had no connection string. The fallback would not have widened; it would have been *published*. Full rule, measured route table and the `force-dynamic` requirement: `.claude/rules/rendering.md` (scoped to `app/**`, where the violation is committed).
