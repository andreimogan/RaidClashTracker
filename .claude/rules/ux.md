UX checklist for user-facing surfaces (enforced on review by `ux-specialist`; implementers should self-check against it):

- **State coverage** — a data surface has **two independent axes**, and conflating them is this project's most repeated UX bug. *Where the numbers come from* (five states) and *whether this visitor may write* (three).

  **Data-source states — five.** The first two are the pair most easily conflated:
  - **Connected but empty** — the database is reachable and migrated, there are just no rows yet (fresh `npm run db:migrate`, or the user pressed Reset in Settings). Renders *genuinely empty*, and **writes work for the admin** — so an empty surface here must not borrow demo mode's read-only copy or imply anything is missing but a first import.
  - **Demo mode** — no `DATABASE_URL`, or the tables don't exist yet (`42P01`) → the bundled sample dataset, **read-only for everybody**. Must say the numbers are not the clan's. A user can move between this state and the one above without touching a config file (Reset), so the two must never look alike.
  - **Loading / pending** — in-flight reads and mutations.
  - **In-place error** — one fetch or save failed; the surface stays usable and surfaces the reason where the action was.
  - **Connection failure** — the render itself throws (wrong password, DNS, paused project, pooler exhaustion) and the root `app/error.tsx` boundary takes over the whole page with a retry. **No surface may fall back to demo data here** — that is the invariant `lib/data.ts`'s `42P01`-or-no-URL allowlist exists to protect, and the copy's job is to say the other pages' numbers are neither stale nor invented.

  **Permission states — FOUR cells, not three. It is a 2×2: `source` (live | demo) × `signedIn` (yes | no).** This list said "three" for one order by collapsing demo into a single row, and that omission is *how* the Admin Access card shipped branching on `signedIn` alone — it offered a "Sign in" link in demo mode, pointing at a page that says sign-in isn't configured. **Check every write affordance against all four:**
  - **Live + anonymous** — reads everything, writes nothing. Affordances **absent**; copy says **"sign in"** and links to `/login`, because signing in is the fix.
  - **Live + admin** — the only state where a write control belongs on screen. **Also the hardest to verify**: only the owner has the password, so if you cannot render it, say so in the changelist rather than implying you did. (Rendering it behind a temporary stub proves *branch selection and copy*, never the session path — label it that way.)
  - **Demo + anonymous** — nobody can write. Copy says **"connect the clan database"**, because that is the fix, and shows **no `/login` link at all**: signing in would leave writes still failing, and in this state the login page cannot even be configured. **Never the sign-in sentence here.**
  - **Demo + admin** — the cell that gets forgotten, and the one that produced the bug above. Reachable whenever the auth env is set but the database is not: typo'd `DATABASE_URL`, unmigrated tables, a **paused free-tier project**. The reader *is* the admin and must not be told to sign in, but writes are still locked. Name both facts, keep sign-out reachable, and do not promise that anything is unlocked. **When both blockers apply, demo wins the copy** — it is the one that survives signing in.

  Threaded as `readOnly: boolean` + `readOnlyReason: "anonymous" | "demo" | null`, computed once per page (`app/settings/page.tsx`, `app/members/[memberId]/page.tsx`) and passed down; **`readOnly` is the established prop name — do not invent a second one.** **Three read-only reasons need three distinct copies**: sign-in, connect-the-database, and connected-but-empty (which is not read-only at all — it needs a first import, not a permission). **When both blockers apply, demo mode wins the copy**, because it is the one that survives signing in.

  Never render an action that cannot succeed in the current state; **hide it** with a reason rather than disabling it (precedent: pencils hidden + read-only note in `MemberHistoryTable`; the `/api/backup` link is not rendered at all for a non-admin). Prefer **splitting** a gated component — keep the interactive body in an inner component behind a thin wrapper that switches on `readOnly` — over an early `return` inside it: an early return in front of `useState`/`useRef`/`useRouter` is a conditional hook call (`react-hooks/rules-of-hooks`), and the split has the better security property anyway, since the file picker, POST helpers and pending state then **do not exist in the tree** for a reader who could never save. Precedent: `DataManagement`/`DataTools`, `ImportPanel`/`ImportForm`, `AvatarEditor`/`AvatarUploader`.
- **Feedback** — after a mutation, reflect the result: the app's convention is POST → check `res.ok && data.ok` → `router.refresh()`, with a pending spinner (`Loader2`) and errors surfaced in-place (`text-xs text-down`, `whitespace-pre-line` for multi-line messages). Don't leave an action with no visible outcome.
- **Destructive / lossy actions** — confirm before irreversible or data-losing operations (precedent: type-`RESET` confirm; overwrite-confirm on import). Avoid silently writing rounded/derived values back over exact stored data.
- **Accessibility** — modals: initial focus inside, focus trap while open, restore focus on close, Escape to dismiss, `role="dialog"` + `aria-modal`. Icon-only buttons need `aria-label`. Keyboard-operate every control. **Contrast: `text-faint` (`--color-faint #586478`) measures ~3.05:1 on card surfaces and cannot reach WCAG AA at any size used here** — `html { font-size: 75% }` puts `text-xs` at ~10.5px, far below the large-text exemption. `text-muted` measures ~6.23:1 and passes. So `text-faint` is for genuinely decorative text only; **never use it for anything the reader needs** (instructions, error explanations, labels on a value they must act on). Measured 2026-08-12; existing `text-faint` uses in `components/MemberHistoryTable.tsx` are known debt, queued for the demo/empty-state UX order.
- **Content & clarity** — labels and microcopy legible to non-power-user clanmates; keep RAID/clash terminology consistent with **`README.md`**, which is the app's user-facing doc. *(This used to point at `ONBOARDING.md` / `TUTORIAL.md`. Both document the agent scaffold, not the app — zero occurrences of import/edit/reset/avatar/sign-in vocabulary in either — so the pointer sent every reviewer to the wrong place.)*
- **Copy on a public surface must not leak — and here is exactly where the line is**, because the first draft of this rule was over-broad and contradicted a page shipped in the same order. Every page is readable by anyone, so nothing rendered may contain a **secret or an identifier of the hosting project**: a connection string or any part of one, a host, a key, the Supabase project ref, the admin email, or a raw driver message (postgres.js builds connection errors as `write/connect <code> <host>:<port>`, and a `28P01` message carries the user name that embeds the project ref). **Naming the auth vendor is also out** on `/login` specifically — a login page that announces which identity provider sits behind it hands a prober a starting point for free.
  **What is deliberately allowed:** the operator runbook on `/settings` names `DATABASE_URL`, `.env.local`, `npm run db:migrate` and `npm run import`. Those are setup instructions for whoever runs the server, they are already public in `README.md`, and in demo mode — the only state a stranger plausibly sees them in — there is no clan data to protect. Removing them would cost the owner their only in-app runbook to buy nothing. **So: no values, no host, no key, no project identity, no vendor name on `/login`; variable *names* and npm scripts in setup copy are fine.** Decided 2026-08-12 after two reviewers flagged the collision from opposite sides; do not silently re-tighten it. Sign-in failures collapse to **one** message for wrong password, unknown address, unconfirmed account and disabled signup alike, so the UI can never be used to discover whether an account exists; rate limiting is the only failure worth naming separately, because it says nothing about the credentials and otherwise a locked-out owner reads "didn't match" and keeps retrying. See `docs/reference/auth.md`.

This is a review lens, not an ownership grant — `ux-specialist` reports; `ui-design-specialist` (or the owning implementer) makes the changes.
