UX checklist for user-facing surfaces (enforced on review by `ux-specialist`; implementers should self-check against it):

- **State coverage** — a data surface has **two independent axes**, and conflating them is this project's most repeated UX bug. *Where the numbers come from* (five states) and *whether this visitor may write* (three).

  **Data-source states — five.** The first two are the pair most easily conflated:
  - **Connected but empty** — the database is reachable and migrated, there are just no rows yet (fresh `npm run db:migrate`, or the user pressed Reset in Settings). Renders *genuinely empty*, and **writes work for the admin** — so an empty surface here must not borrow demo mode's read-only copy or imply anything is missing but a first import.
  - **Demo mode** — **no connection string resolves** (neither `DATABASE_URL` nor, on a deployment, the integration's `POSTGRES_URL` holds a non-blank value), or the tables don't exist yet (`42P01`) → the bundled sample dataset, **read-only for everybody**. Must say the numbers are not the clan's. **Write copy about the *state*, not about `DATABASE_URL`:** on the deployed site the fix is usually reconnecting the Supabase↔Vercel integration, not setting a variable named `DATABASE_URL`, so "connect the clan database" is the durable sentence and "set `DATABASE_URL`" is only correct locally. (The one place variable names are deliberately allowed is `/settings`'s operator runbook — see the leak rule at the bottom.) A user can move between this state and the one above without touching a config file (Reset), so the two must never look alike.
  - **Loading / pending** — in-flight reads and mutations. **A placeholder is a claim that *this* data is loading, so it must be scoped by the data, not by the page:** only surfaces fed a `selectedWeek` argument (`getOverview`, `getKeyUsageSummary`, `getPerformance`) swap during a week change; all-weeks surfaces must **not**, even when the selected week is passed to them for a highlight (`getTimeline` → `TimelineStrip` / `WeeklyBarChart`; `getAllWeeksTotals` → the "Total (All Weeks)" tab; `getBlackList` → `BlackListTable`, which takes no week argument at all and so reads no transition state), and `/timeline` and `/members` therefore ship **zero** — `/timeline` because every surface on it is all-weeks, `/members` because it has **no week control at all** (its roster aggregates every week, so the picker that changed nothing was removed on 2026-08-13 and `TopBar` renders none there). Week-independent chrome (icons, labels, table headers, search, sort, **and the pagination control under every table**) stays real and interactive — that is what makes a half-swapped screen read as refreshing rather than broken. **The page index is chrome too, and its rule has TWO halves that turn on who caused the change — shipping only the first reads as a blanket never-reset, which is wrong.** (a) **A change the app makes to the reader — a week change — clamps, never resets.** `usePagination` (`components/Pagination.tsx:160`) holds the page the reader *asked* for and hands back that request clamped into the current `[1, pageCount]` (`components/Pagination.tsx:148`), so a shorter incoming week folds page 4 of 4 down to page 2 of 2 with rows in it instead of a blank slab; resetting there would throw away a position the reader chose. (b) **A change the reader asks for — search, sort, tab, filter — DOES reset to page 1, from the event handler that caused it** (`components/PerformanceTable.tsx:134`, `:190`, `:207`; `components/ClashTable.tsx:79`, `:127`). The clamp is no help for those: page 3 of 3 is still *in range* after a search cuts 30 rows to 22, so the reader types a name and is shown matches 21–22 as if that were everything the search found. **Neither half is ever written as an effect — and the reason is the frame, not the linter.** An effect *commits and paints* one wrong frame (`21-22 of 22`) before correcting itself; React's documented render-phase adjustment is discarded and re-run before it reaches the DOM (`components/TotalPerformanceTable.tsx:113-117`). **`react-hooks/set-state-in-effect` will NOT catch the effect version here**: the rule cannot follow a setter that arrives through a custom hook's return value, so for all six `usePagination` consumers there is no guardrail at all. Measured both ways in the 2026-08-17 fix round (via `view.setPage`: an `exhaustive-deps` warning only; with the setter destructured first: nothing new at all) and recorded at `components/TotalPerformanceTable.tsx:88-104`. This doc previously claimed lint was the guardrail — it is not; cite the painted frame. Feedback still belongs at the control on the no-placeholder pages: spinner plus an `sr-only` `role="status"` announcing **both** the start and the completion, since a query-only navigation announces nothing by itself — and that region is owned by `WeekTransitionProvider`, not by the bar, so it survives a sidebar navigation instead of being re-inserted already populated. **There are exactly TWO week-change entry points and both must run through `startWeekChange`: `components/TopBar.tsx` (the `<select>` + both chevrons) and `components/TimelineStrip.tsx` (the week cards) — `grep -rn 'set("week"' components/` must return those two sites and no others.** Full pattern: `docs/reference/design-system.md`, "Week-change pending swap".
  - **In-place error** — one fetch or save failed; the surface stays usable and surfaces the reason where the action was.
  - **Connection failure** — the render itself throws (wrong password, DNS, paused project, pooler exhaustion) and the root `app/error.tsx` boundary takes over the whole page with a retry. **No surface may fall back to demo data here** — that is the invariant `lib/data.ts`'s `42P01`-or-no-URL allowlist exists to protect, and the copy's job is to say the other pages' numbers are neither stale nor invented.

  **Permission states — FOUR cells, not three. It is a 2×2: `source` (live | demo) × `signedIn` (yes | no).** This list said "three" for one order by collapsing demo into a single row, and that omission is *how* the Admin Access card shipped branching on `signedIn` alone — it offered a "Sign in" link in demo mode, pointing at a page that says sign-in isn't configured. **Check every write affordance against all four:**
  - **Live + anonymous** — reads everything, writes nothing. Affordances **absent**; copy says **"sign in"** and links to `/login`, because signing in is the fix.
  - **Live + admin** — the only state where a write control belongs on screen. **Also the hardest to verify**: only the owner has the password, so if you cannot render it, say so in the changelist rather than implying you did. (Rendering it behind a temporary stub proves *branch selection and copy*, never the session path — label it that way.)
  - **Demo + anonymous** — nobody can write. Copy says **"connect the clan database"**, because that is the fix, and shows **no `/login` link at all**: signing in would leave writes still failing, and in this state the login page cannot even be configured. **Never the sign-in sentence here.**
  - **Demo + admin** — the cell that gets forgotten, and the one that produced the bug above. Reachable whenever the auth env is set but no database resolves: typo'd `DATABASE_URL`, unmigrated tables, a **paused free-tier project**, or — on the deployed site — a **missing or blank `POSTGRES_URL`** because the Supabase↔Vercel integration was disconnected or a name was saved with no value. That last route is the one this project actually shipped (Phase 4: a public URL serving demo data), and it is why the copy here must not name a variable the reader may not even own. The reader *is* the admin and must not be told to sign in, but writes are still locked. Name both facts, keep sign-out reachable, and do not promise that anything is unlocked. **When both blockers apply, demo wins the copy** — it is the one that survives signing in.

  Threaded as `readOnly: boolean` + `readOnlyReason: "anonymous" | "demo" | null`, computed once per page (`app/settings/page.tsx`, `app/members/[memberId]/page.tsx`) and passed down; **`readOnly` is the established prop name — do not invent a second one.** **Three read-only reasons need three distinct copies**: sign-in, connect-the-database, and connected-but-empty (which is not read-only at all — it needs a first import, not a permission). **When both blockers apply, demo mode wins the copy**, because it is the one that survives signing in.

  Never render an action that cannot succeed in the current state; **hide it** with a reason rather than disabling it (precedent: pencils hidden + read-only note in `MemberHistoryTable`; the `/api/backup` link is not rendered at all for a non-admin).

  **That rule is about PERMISSIONS, and there is a third case it does not cover: a control that is momentarily unusable but must stay reachable.** Pagination's prev/next at the ends of a range are neither hidden nor natively `disabled`. Not hidden, because "you are on the last page" is a transient *position*, not a permission, and a control that vanishes at the ends makes the whole chrome row jump on every navigation. Not `disabled`, because the native attribute costs the keyboard reader their place: the browser cannot keep focus on a disabled element, so paging to the last page — the ordinary happy path, on six surfaces — drops focus to `<body>` and the next Tab restarts at the top of the document, and the button is skipped by Tab thereafter. The shipped form is **`aria-disabled` plus a no-op guard as the first statement of each handler** (`components/Pagination.tsx:263`, `:266`, `:278`, `:281`), with the dim and the hover suppression moved onto the `aria-disabled:` variant, since `:disabled`/`:enabled` no longer match anything (`components/Pagination.tsx:107-110`). One more wrinkle in the same spirit: at `pageCount === 1` the button group *and* its `<nav>` are dropped entirely (`components/Pagination.tsx:253`) — a permanently-dead chevron pair is not a transient position, and a "…pagination" landmark with nothing to navigate is a false promise in a landmark list. **`components/TopBar.tsx:129-144` still carries the native `disabled` on both week chevrons and therefore still has the focus defect.** It is where this shape was inherited from; it is unowned and is a queued follow-up, not a precedent to copy.

  Prefer **splitting** a gated component — keep the interactive body in an inner component behind a thin wrapper that switches on `readOnly` — over an early `return` inside it: an early return in front of `useState`/`useRef`/`useRouter` is a conditional hook call (`react-hooks/rules-of-hooks`), and the split has the better security property anyway, since the file picker, POST helpers and pending state then **do not exist in the tree** for a reader who could never save. Precedent: `DataManagement`/`DataTools`, `ImportPanel`/`ImportForm`, `AvatarEditor`/`AvatarUploader`. The same shape is the answer for an **optional** control too, not just a gated one: `TopBar`/`WeekPicker` (`components/TopBar.tsx`) keeps the three week-transition hooks out of the tree on a page that passes no week props.
- **Feedback** — after a mutation, reflect the result: the app's convention is POST → check `res.ok && data.ok` → `router.refresh()`, with a pending spinner (`Loader2`) and errors surfaced in-place (`text-xs text-down`, `whitespace-pre-line` for multi-line messages). Don't leave an action with no visible outcome.
- **Destructive / lossy actions** — confirm before irreversible or data-losing operations (precedent: type-`RESET` confirm; overwrite-confirm on import). Avoid silently writing rounded/derived values back over exact stored data.
- **Accessibility** — modals: initial focus inside, focus trap while open, restore focus on close, Escape to dismiss, `role="dialog"` + `aria-modal`. Icon-only buttons need `aria-label`. Keyboard-operate every control. **Contrast: `text-faint` (`--color-faint #586478`) measures ~3.05:1 on card surfaces and cannot reach WCAG AA at any size used here** — `html { font-size: 75% }` puts `text-xs` at ~10.5px, far below the large-text exemption. `text-muted` measures ~6.23:1 and passes. So `text-faint` is for genuinely decorative text only; **never use it for anything the reader needs** (instructions, error explanations, labels on a value they must act on). Measured 2026-08-12; existing `text-faint` uses in `components/MemberHistoryTable.tsx` are known debt, queued for the demo/empty-state UX order.
- **Content & clarity** — labels and microcopy legible to non-power-user clanmates; keep RAID/clash terminology consistent with **`docs/user-guide.md`**, which is the app's user-facing doc. *(This pointer has now drifted twice, so check it before you trust it. It first pointed at `ONBOARDING.md` / `TUTORIAL.md` — both document the agent scaffold, not the app, with zero occurrences of import/edit/reset/avatar/sign-in vocabulary in either — so it sent every reviewer to the wrong place. It was then repointed at `README.md`, which was true only until the same order that wrote `docs/user-guide.md` moved every user-facing behaviour out of `README.md` and made it a hub of links. Whichever doc actually names the metrics, the actions and the states in the user's words is the one this line means; `README.md` no longer does.)*
- **Copy on a public surface must not leak — and here is exactly where the line is**, because the first draft of this rule was over-broad and contradicted a page shipped in the same order. Every page is readable by anyone, so nothing rendered may contain a **secret or an identifier of the hosting project**: a connection string or any part of one, a host, a key, the Supabase project ref, the admin email, or a raw driver message (postgres.js builds connection errors as `write/connect <code> <host>:<port>`, and a `28P01` message carries the user name that embeds the project ref). **Naming the auth vendor is also out** on `/login` specifically — a login page that announces which identity provider sits behind it hands a prober a starting point for free.
  **What is deliberately allowed:** the operator runbook on `/settings` names `DATABASE_URL`, `.env.local`, `npm run db:migrate` and `npm run import`. Those are setup instructions for whoever runs the server, they are already public in `README.md`, and in demo mode — the only state a stranger plausibly sees them in — there is no clan data to protect. Removing them would cost the owner their only in-app runbook to buy nothing. **So: no values, no host, no key, no project identity, no vendor name on `/login`; variable *names* and npm scripts in setup copy are fine.** Decided 2026-08-12 after two reviewers flagged the collision from opposite sides; do not silently re-tighten it. Sign-in failures collapse to **one** message for wrong password, unknown address, unconfirmed account and disabled signup alike, so the UI can never be used to discover whether an account exists; rate limiting is the only failure worth naming separately, because it says nothing about the credentials and otherwise a locked-out owner reads "didn't match" and keeps retrying. See `docs/reference/auth.md`.
