## Overview

Web dashboard for a RAID: Shadow Legends clan's **Hydra Clash** and **Chimera Clash** performance — per-member keys used, damage, participation, and week-over-week trends. It runs both on the owner's machine (`npm run dev`) and **deployed on Vercel** (per the owner's report, `main` is the production branch, auto-deploying on push — not verifiable from the repo, so treat it as reported rather than measured); the database is hosted. **Reads are public; every write is admin-only** — one account, signed in at `/login`, authorized by an `ADMIN_EMAIL` match (see `docs/reference/auth.md`).

Stack: **Next.js 16 (App Router, TypeScript) · Tailwind CSS v4 · Recharts · lucide-react · Supabase Postgres 17 via `postgres` (postgres.js)** reached over a pooled (`:6543`) connection URI with `prepare: false`, plus **Supabase Auth via `@supabase/ssr`** (`2.112.3` / `0.12.4`) for sign-in only — never for data. The app reads **exactly four** environment variables: the connection URI (`DATABASE_URL`, else the integration's `POSTGRES_URL`), `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `ADMIN_EMAIL`. **A Vercel deployment needs no manual `DATABASE_URL`** — the Supabase↔Vercel integration's `POSTGRES_URL` is picked up as-is, and the two names the integration also creates (`POSTGRES_URL_NON_POOLING`, `POSTGRES_PRISMA_URL`) are deliberately never read. **One Supabase project serves production, every preview deployment and local dev**, so a preview writes production data. See `docs/reference/deployment.md`.

> **Superseded decision — SQLite / libSQL / Turso.** The project's previously *locked* deploy path was **Turso**, a hosted drop-in for the local **SQLite** file (`data/clash.db`) that the app reached through **`@libsql/client`** — the appeal being a deploy with no code change at all. Phase 2's port to Supabase Postgres **supersedes** it: `@libsql/client` is uninstalled, no database file is read at runtime, and dual-engine SQL compatibility is no longer a constraint. The engine names stay written out here so a reader carrying the old vocabulary can grep for them and find this line; `docs/build-log.md` records both decisions and why the second replaced the first.

## Structure

- `app/` — routes: `/` (overview), `/hydra`, `/chimera` (per-clash detail), `/timeline` (weekly totals), `/members` + `/members/[memberId]` (roster/detail), `/settings` (clan info, data management, import tab), `/import` (**not a page** — a two-line `redirect("/settings")` that answers **307**; the import UI is the Settings "Import data" tab, and this path is kept working only so old links don't break — `app/import/page.tsx:5`), `/login` (sign-in; **deliberately absent from the sidebar** — see `docs/reference/auth.md`)
- `app/api/` — the write surface: `import` (JSON, upsert/replace), `backup`, `restore`, `reset`, `members/[memberId]/results`, `members/[memberId]/avatar`. **All six are admin-only:** each handler opens with `requireAdmin()` as the first statement of its body and returns a frozen 401 JSON body to anyone else, issuing no database query. `backup` is gated as an **exfil** route, not a read — it exports the whole dataset.
- `proxy.ts` (repo root) — token refresh, and nothing else. **The file convention is `proxy`, not `middleware`, in this Next version; a `middleware.ts` is silently ignored.** It never blocks a request and no-ops when the Supabase env vars are absent.
- `app/login/` — `page.tsx` + `LoginForm.tsx` + `actions.ts`. `actions.ts` holds the **only** `"use server"` functions in the repo (`signIn`, `signOut`); no data write goes through a Server Action, so `requireAdmin()` stays the single choke point.
- `components/` — 21 UI components in the gestal.gg aesthetic (dark panels, hairline borders, Hydra amber / Chimera steel-blue). All styling flows from tokens/primitives in `app/globals.css`.
- `lib/` — the seams:
  - **Read path:** `data.ts` `loadDataset()` reads members / weeks / clash_results / clash_meta from Postgres → `compute.ts` derives all metrics (data-source agnostic). It exposes `DataSource = "postgres" | "demo"`, and its four row mappers are the **single coercion boundary** (Postgres `bigint` reads back as a JS string; every numeric field is wrapped in `Number(...)`). It falls back to `mock-data.ts` (bundled demo, weeks 20–24) **only** when `databaseUrl()` is null (no non-blank `DATABASE_URL` *or* `POSTGRES_URL`) or the error code is `42P01` (undefined table) — every other failure rethrows to `app/error.tsx`. A reachable but empty database renders genuinely empty.
  - **Write path (the only one):** `parse.ts` (parseCsv / parseDamage) → `import.ts` (normalizers — pure, client-safe) → `persist.ts` `persist(payload, "upsert" | "replace")`, which runs every statement in one transaction.
  - `db.ts` — exactly one database and exactly four exports: `type Db` (a re-export of postgres.js's client type, which is named **`Sql`**, so nothing else imports `postgres` directly), `databaseUrl(): string | null` (the first **non-blank, trimmed** value of `DATABASE_URL` then `POSTGRES_URL`, so a **blank value counts as unset** — a commented-out or emptied env line must land in demo mode rather than on an error page, and must not shadow the next name in the chain; never logged, returned to a client, or rendered, because it contains the password. Deliberately a loop and not `a ?? b`: `""` is not nullish, so a `??` chain would let an empty `DATABASE_URL` silently beat the platform's `POSTGRES_URL`), `getDb(): Db` (throws a clear error naming **both** variables when neither is set, and warns once per process — port and variable name only, never the URI — when the resolved URI is not on the pooled `6543`; it never throws for a wrong port), and `closeDb(): Promise<void>` (`sql.end()`, so the CLI entries can exit). The pool is a **`globalThis` singleton** — a module `const` would open a pool per Next dev HMR reload and exhaust the pooler — configured with `prepare: false` (mandatory on the transaction pooler), `max: 3`, and an `idle_timeout`. No filesystem I/O. **`max` is a correctness bound:** exceeding it with concurrent queries deadlocks against the transaction pooler, so a multi-query read runs inside one `begin("read only", …)` — see `.claude/rules/database.md`. The in-transaction client is `TransactionSql`, which is **not** assignable to `Db`.
  - **Auth path (the whole authorization surface):** `supabase/server.ts` `createServerSupabase()` — a `@supabase/ssr` server client wired to `await cookies()`, used for `auth.*` **only** (no `.from(`, no `/rest/v1` anywhere) and returning `null` when the Supabase env vars are absent → `auth.ts`, which exports exactly two names: `isAdmin()` (never throws — `false` on any doubt, wrapped in React `cache()`) and `requireAdmin()` (**returns** a 401 `NextResponse`, never throws, because a throw would become a 500 with a Next digest instead of the JSON body the client components render). `lib/supabase/client.ts` **deliberately does not exist** — no Supabase client is created in the browser and the publishable key never enters the bundle. `isAdmin()` is read in exactly two pages and **never in `app/layout.tsx`**: `cookies()` is a request-time API, so reading it there would opt every route into dynamic rendering and undo the static `/import`.
  - `week.ts` (UTC clash schedules), `types.ts`, `format.ts`, `constants.ts`, `backup.ts`, `members.ts`, `results.ts`, `seed.ts`.
- `supabase/migrations/` — numbered, forward-only SQL files, applied in filename order by `npm run db:migrate` (safe to re-run). An applied migration is never edited; a change means a new numbered file.
- `scripts/` — CLI entries (`db-migrate`, `seed`, `import-csv`, `import-json`); each imports `scripts/lib/load-env.ts` first and closes the pool so the process exits.
- `data/` — sample datasets, tracked: `sample-import.csv`, `sample-week-flat.json`, `sample-week.json` (the owner's archived SQLite files live here untracked and are no longer read). `Database/` — tracked real in-game exports, currently `test-week.json`, a flat array; it is the shape `lib/import.ts:107` cites. `Assets UI/` — design references.
- `docs/` — `README.md` is the hub; `docs/engineer-onboarding.md` (setup → deploy, trip hazards) and `docs/user-guide.md` (admin operations, metric meanings, destructive actions) are the two human entry points; `docs/reference/{auth,data-pipeline,deployment,design-system}.md` are the living references; `docs/build-log.md` is append-only history and `docs/tasks/` is the runtime work queue, **not documentation — nothing links to it**.

## Key entities / modules

- **Dataset** (from `loadDataset()`) is the architecture seam between storage and UI — pages consume it, `compute.ts` derives from it, and its shape is identical in every data state. No file outside `lib/data.ts` compares `getDataSource()` against a storage literal; call sites test `=== "demo"` / `!== "demo"`.
- **Clash semantics:** Hydra = 3 keys/member, Wed→Wed (UTC); Chimera = 2 keys/member, Fri→Thu (UTC); both clashes of week *N* share a calendar week. Dates are derived, never user-entered.
- **Ingest semantics:** three entry points, one pipeline. In-app JSON import = replace of its `(week, clash)`; legacy nested JSON = upsert (back-compat); CSV file (`npm run import`) = upsert; member week edit = upsert of that member's two clash rows. Damage accepts number, `"16.61B"` shorthand, or `null` (benched → 0). **The terminal is not uniformly the "safe" half:** `npm run import:json` picks its mode from the file's shape, so a **flat array replaces** that `(week, clash)` (`scripts/import-json.ts:44`) exactly as the in-app path does, and only the nested `{ week, clashes }` object upserts (`scripts/import-json.ts:50`).

## Open unknowns / blockers

- **No test suite** — verification is `npm run build` + manually exercising the affected page. A future order could add one.
- **Preview deployments read and write production data.** One Supabase project, so every preview inherits the same connection URI; a preview's Import/Restore/Reset hits the clan's real rows (416 `clash_results` across 30 members / 7 weeks). Writes still need the admin session, so the risk is the owner acting on a preview URL believing it is a sandbox — nothing in the UI distinguishes them. A second project for previews was considered and not taken. `docs/reference/deployment.md`.
- **Free tier: no automated backups, and a project pauses after ~1 week idle.** `GET /api/backup` is the only backup. A paused project correctly reaches `app/error.tsx` (not demo mode) — and is the case most likely to tempt someone into widening the demo fallback.
- **The deployed runtime is unmeasured from this side.** No agent has Vercel access, so the deploy-side facts (production branch, which variables the project holds, integration state) are the owner's report; only the code and the local build were measured.
- **The signed-in half of the login wall ships unexercised.** Nobody but the owner has the password, so the cookie write, session persistence, the Sign out form and every admin-visible affordance in its rendered state were never run — only their signed-out counterparts were measured. The owner's acceptance test (sign in → edit a week → export a backup → sign out) is what closes it; a pre-approved fallback to Supabase's browser-client pattern exists if it fails. `docs/reference/auth.md`, *What ships unexercised*.
- **`/login` has no navigation entry point** outside `/settings` and the member pages. Accepted as designed (one account, signups disabled, a public dashboard shouldn't advertise a login door) — recorded so nobody "repairs" it with a sidebar link without asking.
- **`Assets UI/` folder** — design references exist but their intended workflow (manual vs. Figma-driven) is not established.
- **A `TrendBadge` safeguard is defeated at one call site (open bug, found 2026-08-13, deliberately not fixed in a docs-only order).** `components/TrendBadge.tsx:4-5` documents that `value === null` means "no comparable baseline" and renders an em-dash "instead of a misleading flat 0%", and the member page passes `null` through intact (`lib/compute.ts:276`). But the clash tables coerce it first: `deltaPct(thisPerKey, prevPerKey) ?? 0` at `lib/compute.ts:162`. So on `/hydra` and `/chimera` a member with no prior week renders **`0%`**, indistinguishable from "unchanged", and the CSV export of that view inherits the same `0`. Fixing it means letting `trendPct` be `number | null` through `ClashTable`; the fix is small, the type ripple is the reason it is recorded rather than done. Documented as user-visible in `docs/user-guide.md`.
- **`npm run import` with no argument fails with a raw `ENOENT`.** `scripts/import-csv.ts:12` defaults the positional to `data/import.csv`, **a file this repo does not ship** — the tracked samples are `data/sample-import.csv`, `data/sample-week-flat.json` and `data/sample-week.json`. `readFileSync` throws before any usage message. Either ship the default file, point the default at the sample, or print usage. Not fixed (docs-only order).
