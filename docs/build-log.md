## 2026-07-06 — Edit a member's weekly clash stats from their history table

- **Built:** Per-week edit dialog on the member detail page. The Week-by-Week History table now lists **all** tracked weeks (weeks the member missed show as "—" and can be filled in); a pencil per row opens the app's first modal with four fields (Hydra/Chimera keys and damage, `"16.61B"` shorthand accepted with live preview). New `POST /api/members/[memberId]/results` + `lib/results.ts` writes both clash rows through `persist(payload, "upsert")` — the sanctioned pipeline, no direct SQL. New shared component `components/MemberHistoryTable.tsx`; CSV export follows the merged rows.
- **Decisions:** All-weeks merge done in the page, not `lib/compute.ts` (its present-weeks semantics feed lifetime stats). Endpoint validation stricter than imports: member and week must pre-exist, dates and display name come from **stored** records (client values are validation-only), keys integer-capped at `MAX_KEYS`, garbage damage strings rejected instead of coerced to 0. Demo mode guarded on both sides (pencils hidden + endpoint 400). Dialog is a hand-rolled fixed overlay + `.card` panel — now the documented modal pattern.
- **Rejected:** Inline cell editing (user chose dialog); extending `lib/import.ts` validation (would change sheet/JSON import behavior); native `<dialog>` (more plumbing, no gain).
- **Notes:** Review caught and fixed pre-finalize: lossy damage prefill (`formatDamage` rounding would have written rounded values back on save — now prefills exact digits), a member-rename side channel via slug-equivalent `memberName`, and a damage grammar accepting multiple dots. Endpoint smoke-tested against the test DB (21/21). Known-acceptable LOWs: emptied keys field means 0 (benched semantic), autofocus without a full focus trap, double dataset query per page render. Ledger: `docs/tasks/member-week-edit.md` (done).

## 2026-07-06 — Added ux-specialist role

- **Decision:** Added a read-only `ux-specialist` agent (via `/add-role`) — a design-focused counterpart to `flow-reviewer` that reviews a change across four lenses: flow & interaction, accessibility (keyboard/focus/ARIA/contrast), state coverage (empty/loading/error/demo), and content & clarity. It reports findings; `ui-design-specialist` (or the owning implementer) applies them.

- **Fit check:** No ownership overlap with `ui-design-specialist` — that agent *writes* to the visual system; `ux-specialist` is read-only and hands off findings. Considered folding UX into ui-design-specialist or making it a writing agent (shared `components/**`); chose the read-only reviewer split for the cleanest separation and no per-order file-ownership contention.
- **Generated:** `.claude/agents/ux-specialist.md` (tools: Read, Grep, Glob, Bash — inspection only), `.claude/rules/ux.md` (UX checklist scoped to `components/**`, `app/**`), plus this note and a project-map roster entry. Existing agents untouched.

## 2026-08-07 — Import week picker: "has data" now follows the selected clash

- **Built:** In the Settings → Import panel, each week's `has data` / `no data` tag is now computed for the *selected* clash (`existingData[n]?.[clashType]`) instead of the Hydra+Chimera sum, so a week with only Hydra rows correctly reads "no data" under Chimera. The `weekNumber`/`clashType` state moved above the `weekOptions` memo so it can close over `clashType` (the memo previously couldn't see it, so labels wouldn't have recomputed on toggle even with the right formula). The dropdown's listed date range likewise follows the selected clash's window. `importJson()` and `syncSheet()` now `router.refresh()` on success, so the tags and overwrite warning stop showing pre-import state.
- **Decisions:** Display-only fix — no DB, API, or pipeline change. The data was already per-clash (`app/settings/page.tsx` builds `{ hydra, chimera }` per week) and the component already used it correctly for the overwrite warning; only the dropdown derivation was wrong. `canonical = clashWindow(wed, "hydra")` deliberately stays Hydra-anchored: it is the canonical stored week row and part of the write path, and the server re-derives it anyway (`app/api/import/route.ts`) — only dates *displayed* became clash-relative.
- **Rejected:** Adding a weeks-status API endpoint or a clash-aware DB query — the server-rendered `existingData` prop already carries the split, and Settings is `force-dynamic`, so `router.refresh()` suffices. Also rejected making the tag mean "results were imported": `lib/results.ts` writes both clash rows (0/0 when benched), so "has data" means "rows exist and a replace would delete them" — which is exactly what the adjacent overwrite warning promises.
- **Notes:** Review (`flow-reviewer`) confirmed the write path is untouched and the 4 `npm run lint` errors in this file are pre-existing (verified against HEAD). Fixed post-review: the confirm-overwrite row stayed armed after a successful replace (newly adjacent to the success banner because of the refresh), `res.ok` wasn't checked alongside `data.ok` per `.claude/rules/ux.md`, and the clash toggle lacked `aria-pressed`/group labelling — now load-bearing since toggling silently rewrites the `<select>`'s option text. Accepted as-is: sheet sync can re-anchor `currentWeek` mid-session (latent before, now visible without a reload). Ledger `docs/tasks/import-clash-aware-week-tags.md` was backfilled — the order was dispatched as a single one-file slice without one. `npm run build` passes.

## 2026-08-11 — Member history Trend column: week-over-week total damage

- **Built:** The Trend column on `/members/[memberId]` now compares a week's **total damage** against the member's most recent prior *present* week, as ±x%, replacing what it actually did before: damage-per-key measured against the unweighted mean of that same per-key figure across all the member's prior weeks (a cumulative lifetime average — neither total damage nor week-over-week). New exported `deltaPct(current, previous): number | null` in `lib/compute.ts` returns `null` when there is no usable baseline; `MemberWeekRow.trendPct` widened to `number | null`; `TrendBadge` takes `number | null` and renders a `text-muted` em-dash for null. The column header became `Dmg vs Prev Week`, and the CSV export emits an empty cell instead of a fabricated `0`. `formatPct` from `lib/format.ts` — defined since the beginning and never once called — is now the badge's number formatter.
- **Decisions:** Baseline is `presentWeeks[i-1]`, which is exact rather than convenient: `presentWeeks` is already ascending (`sortedWeeks` returns a sorted copy) and already filtered to weeks the member has a row in, so the index lookup *is* "most recent prior present week" and gap-skipping falls out for free. Gaps in tracking are therefore skipped; **a zero-damage (benched) week is not** — it breaks the chain and the following week shows a dash. That was the user's explicit call ("I will not have benched week. Keep the calculation based on previous week"), taken against the UX reviewer's recommendation and in line with the correctness reviewer's: reaching back past a benched week would silently change the column's meaning from "vs last week" to "vs last week I played", with nothing in the badge to tell the reader which they're looking at. A benched week itself still renders −100%, which is honest under the new definition. The no-baseline dash uses `text-muted`, deliberately *distinct* from the absent-week `text-faint` dashes — this reversed acceptance criterion #4 (which had asked them to match) on two grounds: `text-faint` measures ≈3.0:1 on the card gradient and `html { font-size: 75% }` renders `text-sm` at 10.5px, so it fails WCAG AA with no large-text allowance; and "present but no baseline" is a genuinely different state from "no data". Three states now read distinctly: `Minus 0%` flat, muted dash no-baseline, faint dashes absent.
- **Rejected:** Unifying the other two trend meanings — `getPerformance` (dmg/key vs the previous *global* week, single clash) still feeds `ClashTable` and, via `memberClashStat`, the per-clash cards on this same page. Extracting `deltaPct` makes a later unification cheap; doing it now would have widened a display fix into three surfaces. Also declined by the user after review, each a real finding rather than a nit: `sr-only` up/down text (so `-20%` may still be announced as "20 percent", since screen readers speak `+` but often drop the hyphen); folding the per-week totals into one pass (the numerator sums `hydra + chimera` while the baseline uses the unfiltered `"total"` aggregate — equal today *only* because `db/schema.sql:29` constrains `clash_type` to two values, and silently wrong if a third is ever ingested); renaming the CSV `"Trend %"` header, whose meaning changed while its name didn't; and two doc-accuracy nits. No write-path, API, or schema change — display only, per the `import-clash-aware-week-tags` precedent.
- **Notes:** **Solo order** — one ownership group, one implementer, integration skipped (no seams between a slice and itself). Reviewed by `flow-reviewer` (**PASS**, no CRITICAL/HIGH) and `ux-specialist` in parallel; both were run before any user decision, and they *disagreed* on the benched-week baseline, which is what surfaced it as a decision rather than a defect. The correctness review verified rather than trusted: brute-forced `formatPct` against the string it replaced across ±500 at 0.01 steps (0 mismatches), exhaustively compared old vs new trend arithmetic over `{0, -0, ±1, ±1e-4, ±1e12, ±Infinity, NaN}²` (only divergence is `previous === NaN`, unreachable — a NaN key count is falsy and already yields 0), and fed weeks in *descending* order to confirm the `[i-1]` simplification is safe rather than incidentally correct. Corrections to the record: the context pack I wrote claimed `app/members/[memberId]/page.tsx` carries pre-existing lint errors — it does not; at HEAD the only linted-source offender is `ImportPanel.tsx` (4 errors), and the other 6 errors + 1 warning come from the untracked `.claude/scripts/*.js` scaffold. Riding along in this commit but **not part of this order**: the `docs/project-map.md` edit (a resolved "uncommitted work in progress" bullet) and the `.claude/` scaffold changes are from this session's `/bootstrap` run. Accepted debt: the two declined reviewer findings above. Also unfixed and pre-existing: `lib/compute.ts:2` still describes the module as serving "the **Supabase** and mock data paths", stale since the libSQL decision — worth a `maintainer` sweep. Cosmetic: the longer header pushes the table's horizontal scroll in slightly earlier on narrow viewports (wrapper is already `overflow-x-auto`, so nothing clips).
- Cost: est 4.6M → actual 8.5M (+85%) · ~$16.78 · cache 91% · 2 dispatches · pack 29L · plan 1.8M · 2 cache breaks — **read this one as an outlier, not a baseline.** Two model switches mid-order (Fable 5 → Opus 5) caused the 2 cache breaks, against `cache-discipline.md`'s rule to hold the prefix from step 1 to step 7. Planning also ran to 1.8M, not the 420k measured at the gate, because the plan was iterated four times at the gate (a missing cost forecast, then its rationale, then the model-cost question) — that overrun is gate iteration, not survey cost.
