## 2026-08-11 — Member history Trend column: week-over-week total damage

- **Built:** The Trend column on `/members/[memberId]` now compares a week's **total damage** against the member's most recent prior *present* week, as ±x%, replacing what it actually did before: damage-per-key measured against the unweighted mean of that same per-key figure across all the member's prior weeks (a cumulative lifetime average — neither total damage nor week-over-week). New exported `deltaPct(current, previous): number | null` in `lib/compute.ts` returns `null` when there is no usable baseline; `MemberWeekRow.trendPct` widened to `number | null`; `TrendBadge` takes `number | null` and renders a `text-muted` em-dash for null. The column header became `Dmg vs Prev Week`, and the CSV export emits an empty cell instead of a fabricated `0`. `formatPct` from `lib/format.ts` — defined since the beginning and never once called — is now the badge's number formatter.
- **Decisions:** Baseline is `presentWeeks[i-1]`, which is exact rather than convenient: `presentWeeks` is already ascending (`sortedWeeks` returns a sorted copy) and already filtered to weeks the member has a row in, so the index lookup *is* "most recent prior present week" and gap-skipping falls out for free. Gaps in tracking are therefore skipped; **a zero-damage (benched) week is not** — it breaks the chain and the following week shows a dash. That was the user's explicit call ("I will not have benched week. Keep the calculation based on previous week"), taken against the UX reviewer's recommendation and in line with the correctness reviewer's: reaching back past a benched week would silently change the column's meaning from "vs last week" to "vs last week I played", with nothing in the badge to tell the reader which they're looking at. A benched week itself still renders −100%, which is honest under the new definition. The no-baseline dash uses `text-muted`, deliberately *distinct* from the absent-week `text-faint` dashes — this reversed acceptance criterion #4 (which had asked them to match) on two grounds: `text-faint` measures ≈3.0:1 on the card gradient and `html { font-size: 75% }` renders `text-sm` at 10.5px, so it fails WCAG AA with no large-text allowance; and "present but no baseline" is a genuinely different state from "no data". Three states now read distinctly: `Minus 0%` flat, muted dash no-baseline, faint dashes absent.
- **Rejected:** Unifying the other two trend meanings — `getPerformance` (dmg/key vs the previous *global* week, single clash) still feeds `ClashTable` and, via `memberClashStat`, the per-clash cards on this same page. Extracting `deltaPct` makes a later unification cheap; doing it now would have widened a display fix into three surfaces. Also declined by the user after review, each a real finding rather than a nit: `sr-only` up/down text (so `-20%` may still be announced as "20 percent", since screen readers speak `+` but often drop the hyphen); folding the per-week totals into one pass (the numerator sums `hydra + chimera` while the baseline uses the unfiltered `"total"` aggregate — equal today *only* because `db/schema.sql:29` constrains `clash_type` to two values, and silently wrong if a third is ever ingested); renaming the CSV `"Trend %"` header, whose meaning changed while its name didn't; and two doc-accuracy nits. No write-path, API, or schema change — display only, per the `import-clash-aware-week-tags` precedent.
- **Notes:** **Solo order** — one ownership group, one implementer, integration skipped (no seams between a slice and itself). Reviewed by `flow-reviewer` (**PASS**, no CRITICAL/HIGH) and `ux-specialist` in parallel; both were run before any user decision, and they *disagreed* on the benched-week baseline, which is what surfaced it as a decision rather than a defect. The correctness review verified rather than trusted: brute-forced `formatPct` against the string it replaced across ±500 at 0.01 steps (0 mismatches), exhaustively compared old vs new trend arithmetic over `{0, -0, ±1, ±1e-4, ±1e12, ±Infinity, NaN}²` (only divergence is `previous === NaN`, unreachable — a NaN key count is falsy and already yields 0), and fed weeks in *descending* order to confirm the `[i-1]` simplification is safe rather than incidentally correct. Corrections to the record: the context pack I wrote claimed `app/members/[memberId]/page.tsx` carries pre-existing lint errors — it does not; at HEAD the only linted-source offender is `ImportPanel.tsx` (4 errors), and the other 6 errors + 1 warning come from the untracked `.claude/scripts/*.js` scaffold. Accepted debt: the two declined reviewer findings above. Cosmetic: the longer header pushes the table's horizontal scroll in slightly earlier on narrow viewports (wrapper is already `overflow-x-auto`, so nothing clips).

## 2026-08-12 — Phase 2/5: port the data layer to Supabase Postgres

- **Built:** The app now reads and writes **Supabase Postgres 17.6** via **postgres.js 3.4.9** over the transaction pooler (`:6543`, `prepare: false`). New: `supabase/migrations/0001_init.sql` (a hand-port, not a transliteration — `total_damage bigint`, `is_active boolean`, `created_at timestamptz DEFAULT now()`, `keys_used`/`progress` `double precision`, `CREATE OR REPLACE VIEW`, no `PRAGMA`), `scripts/db-migrate.ts` + `npm run db:migrate`, and `app/error.tsx`. `lib/db.ts` was rewritten to exactly four exports (`Db`, `databaseUrl`, `getDb`, `closeDb`) with the client singleton on `globalThis`. `lib/data.ts` now falls back to `lib/mock-data.ts` **only** when there is no `DATABASE_URL` or the error code is `42P01`; every other failure reaches the new error boundary. `lib/persist.ts`, `lib/backup.ts`, `lib/members.ts`, `lib/seed.ts` moved to `$n` placeholders and single transactions. Deleted: `lib/schema.ts` (a runtime `readFileSync` — a Vercel hazard), `scripts/db-init.ts`, `db/schema.sql`, the `db:init` script, and the `@libsql/client` dependency.
- **Superseded decision, named for the record:** the project's previously-locked storage decision — **local SQLite via `@libsql/client` (libSQL), deployable later to hosted Turso with zero code change** — is formally **superseded** by Supabase Postgres as of this entry. It did not survive contact: the schema and query layer carried SQLite-isms (`datetime('now')`, `INTEGER` damage, `CREATE VIEW IF NOT EXISTS`, `?` placeholders, `intMode`) that do not run on Postgres, so the "no application code changes, only the connection string" promise was false. `DATABASE_AUTH_TOKEN` and `file:` URLs are gone. Two knowledge-layer files (`.claude/rules/database.md`, `docs/project-map.md`) mark the supersession and name **SQLite / libSQL / Turso** on those lines deliberately — see the process finding below.
- **Decisions:** Four tasks in two waves, and **wave 1 was designed to be forward-compatible**: t1 (schema), t2 (call sites + error page) and t3 (docs) each build green against *both* the old libSQL code and the ported code, so `npm run build` was exit 0 at every wave boundary — stricter than the no-broken-window rule requires. The device that made it work: rewriting the three `getDataSource()` comparisons to `=== "demo"` type-checks against the old `"sqlite" | "demo"` union *and* the new `"postgres" | "demo"`, because `"demo"` belongs to both. t4 stayed a single task because `lib/db.ts`'s client type change breaks all six consumers simultaneously and `@libsql/client` cannot be removed before its last importer — splitting it would have handed out a slice that could not run the build, i.e. could not be verified. **`bigint` was proven mandatory, not defensive:** the real data's max `total_damage` is **58,280,000,000**, 27× int4's ceiling, so an `INTEGER` port hard-fails on import rather than degrading. **No applied-migrations table** (t4's D5): idempotent `if not exists` DDL is the re-runnability mechanism, because a tracking table desynchronises the moment the owner runs SQL in the Supabase dashboard — the integrator moved the idempotency requirement into `.claude/rules/database.md` as a constraint on *future* migrations, without which D5 would be a latent trap.
- **Rejected:** Splitting into 2a/2b as the roadmap allowed — 2a would have committed docs describing Postgres while the code still spoke libSQL (the exact drift the doc-sync gate exists to prevent) and its only verification would have been "the build still passes on libSQL"; splitting also doubles the ~3.9M overhead component to control a variance it does not touch. Re-exporting `ISql` from `lib/db.ts` (reviewer's call, accepted): "exactly four exports" is a checkable invariant asserted in three places, nothing needs the alias, and passing a `TransactionSql` where `Db` is expected is an immediate compile error rather than a silent trap — the rule now names the type and says to add the export in the change that first needs it. Any `numeric` column anywhere: it returns as a JS **string** exactly like `int8` (confirmed live), which would have reintroduced this phase's own bug class one level down — and since `avg()`/`sum()` over `bigint` *return* `numeric` in Postgres, the `member_clash_averages` view needed explicit `double precision` casts. Fixing the four write routes that still echo raw driver messages (see Notes) — deferred rather than smuggled in, as those files are in no task's `owns`.
- **Two bugs found that the plan did not anticipate, both of which would have bitten Phase 4:** (**F1**) `loadDataset()`'s `Promise.all` of four queries **deadlocks** against the transaction pooler whenever in-flight queries exceed `max` with a warm pool — reproduced 100% at `max=3/conc=4`, `4/8`, `8/16`, `10/12`, while every `conc <= max` and every cold-pool case passed. **No value of `max` is safe**; raising it moves the cliff. Fixed by running both multi-query reads on one connection via `begin("read only", …)`; 30 parallel `loadDataset()` calls at `max: 3` now complete in 1.46 s. Left unfixed this would have hung page renders under the first real concurrent traffic, i.e. after the Vercel deploy. (**F2**) archived `created_at` values restored **3 hours early** — postgres.js applies serializers by the *server-described* OID regardless of JS type, so `$n::timestamptz` routed a naive string through `new Date(...)`, which V8 reads as local time. Fixed in `lib/backup.ts`'s `ts()`, which the fix pass then widened again after finding the zone guard was hiding a **second** bug: any bare-hours offset — `+00` (Postgres' own `timestamptz` text output) and negatives like `-07` — silently became `now()`. This would have shifted every timestamp in Phase 4's import of the real data, with no error.
- **Notes:** `flow-reviewer` **NEEDS CHANGES** (1 HIGH, 4 MEDIUM, 7 LOW; **no CRITICAL, and no code defect in the ported data layer**); `ux-specialist` **needs work** (5 HIGH, 8 MEDIUM, 4 LOW). No slice was bounced. **The HIGH was a two-line frontmatter fix with outsized stakes:** `.claude/rules/database.md`'s `paths:` did not include `lib/data.ts` or `lib/backup.ts` — the two files its own new `sql.begin()` invariant names — so the rule written to stop F1 recurring would not have loaded for the files where F1 lives. Reviewers verified rather than trusted: F1's fix was confirmed complete by enumerating all six fan-out sites; F2's was checked against **the owner's actual archived backup**, which was also validated for Phase 4 feasibility (416/416 damages integer and non-negative, 0 orphan FKs, 0 duplicate ids, `clash_type` domain clean — **the archive will restore**); and `42P01` was proven unable to widen by exercising the driver inside a pipelined transaction (`ConnectionError.code` is a library string; Supavisor's refusal is `XX000`). The fix pass measured something that changed its own design: `unstable_retry` is `startTransition(() => { refresh(); reset() })`, so the error boundary **remounts** — a `useState` retry counter renders `0` forever (instance counts went `2 → 4 → 6` while the counter stayed `0`), hence a module-scoped counter with a 60 s window. ## 2026-08-12 — Phase 3a/5: close the anonymous PostgREST hole (RLS + grant revocation)
